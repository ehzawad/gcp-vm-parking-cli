# Verification

The updated CLI was tested on macOS with Python 3.15; runtime requires Python 3.10+. The final suite passed **88 tests** with `python3 -m unittest discover -s tests -q`. Source compilation and `git diff --check` also pass.

Tests cover mocked up/stop/park/restore, exact resource identity, boot protection, regional snapshot verification, operation polling, lost replies, idempotent recovery, locking and missing mounts. UX tests cover explicit plan mode, real pseudo-terminal approval/cancellation in a subprocess, noninteractive refusal even with `--execute`, readable storage allocation, snapshot import/source/ID protection, unvalidated/stale backup handling, and failure recovery across separate subprocesses without resending the uncertain mutation.

The collision-safe installer was tested in temporary user-owned PATH directories and refuses existing commands. A fresh login shell on the actual Mac resolves the new launcher and successfully runs its help. The new launcher uses private target/configuration/state files outside the repository. Existing lifecycle/storage/SSH commands were not replaced.

Real read-only checks exercised the installed launcher's provider transport: VM/disk status, snapshot listing, storage inventory, snapshot registration using verified provider IDs, up/park previews, and a restore-test preview. The production VM remained stopped with its original boot disk attached, and the retained snapshot remained READY. Registration wrote only local state and marked restore validation false.

The initial UX verification used read-only provider calls. A separately authorized bounded live test then restored a real snapshot and booted the restored OS from its sole attached boot disk on an isolated CPU VM. It passed a forced read-only ext4 integrity check, selected Ubuntu/kernel/systemd checks and nine configuration/home-file hashes, including five home-directory samples. The guest reported kernel `7.0.0-1014-gcp` and success at 8.84 seconds uptime. The restored root UUID and source-snapshot numeric ID matched the pinned provenance. A restricted systemd target prevented normal applications and networking from starting. GPU behavior and ordinary Docker/application startup remain untested; this is scoped OS restore evidence for one snapshot, not a guarantee for later backups.

The first helper attempt lost its serial output before shutdown and did not validate OS boot. The corrected attempt retained evidence while RUNNING, handled a separate boot partition and used existing IAP SSH for helper preparation. A long-running observer's cached access token expired; a fresh read-only client obtained an access token from the existing login and captured the actual boot result. No resource start/create request was repeated to fix capture. All temporary VM/disk resources were removed after validation. No new credentials, persistent grants, firewall changes or broad network access were introduced. The user separately confirmed full teardown of the original VM, boot disk and retained snapshot; the exact original resources were then deleted and provider absence was verified. All recorded operations completed. This teardown was performed outside the lifecycle CLI's park workflow; it leaves no cloud restore copy.

Removed-target status is tested to query provider absence, reject name reuse and refuse startup, allocation or snapshot import. Historical evidence remains separate from an available restore source.

Live diagnostic capture now saves immutable raw serial samples with fsync and atomic per-phase manifests while the exact VM is RUNNING. VM numeric ID, fresh boot timestamp, phase and unique probe nonce are required; empty/stopped output cannot erase retained evidence. Tests cover stale/wrong identity, wrong or partial nonce, embedded log text, rollover and failed durable writes. A separate boot partition is mounted only by UUID/label from the selected restored disk. Helper preparation can use existing authenticated IAP SSH with a fsynced transcript before shutdown; no new keys or network permissions are needed.

Machine paths, actual project/resource identities, runtime journals, private records, logs, credentials and state are excluded from the repository. Example resources and numeric IDs are synthetic.
